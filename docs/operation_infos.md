# Operations Guide

This document is for ops / on-call engineers running the `rental-api` service.
It explains how the observability stack fits together, what knobs exist, and
how to bring it up locally for debugging.

The service exposes three observability surfaces:

| Surface | What | Endpoint / sink |
|---|---|---|
| Logs | Structured JSON log lines (one per event) | stdout — collect with Loki / Promtail or Filebeat |
| Metrics | Prometheus counters and histograms | `GET /metrics` |
| Traces | Distributed spans via OTLP/gRPC | `OTEL_EXPORTER_OTLP_ENDPOINT` — e.g. Jaeger, Tempo, OTel Collector |

A single `request_id` (UUID, generated by `tracing-actix-web` for every HTTP request)
ties the three together: the same id appears in the log line's span fields, in the
`x-request-id` response header, and as the OpenTelemetry trace id's parent span.

---

## 1. Logs

### Format

In `APP_ENV=production` the app writes JSON, one event per line, to stdout.
In `APP_ENV=development` it writes pretty colored output (intended for `cargo run`).

Each line carries the enclosing span's fields, so a handler-level log automatically
includes `request_id`, `http.method`, `http.route`, `http.status_code`, `layer`, etc.

### Shipping

Use any standard sidecar / DaemonSet — Promtail (→ Loki) or Filebeat (→ Elasticsearch).
The container already writes to stdout, so no file rotation is needed; the runtime
captures it.

### Filtering

Verbosity is controlled by the `RUST_LOG` env var (standard `tracing-subscriber`
`EnvFilter` syntax). Default:

```
RUST_LOG=info,sqlx=warn,actix_web=info,h2=off,hyper=off,tonic=off,tower=off,reqwest=off
```

The `h2=off,hyper=off,tonic=off,tower=off,reqwest=off` block is **important when
OTLP is enabled** — without it, the OTel exporter's own gRPC client spans (h2
flow-control internals) would feed back into the trace stream and create noise
in Jaeger / Tempo.

To debug a single subsystem, override at runtime:

```
RUST_LOG=info,sqlx=debug,claude_test::repositories::booking=trace
```

### Correlating a log line with a trace

Every log line emitted inside an HTTP request inherits the span fields, including
`request_id`. To find every log for one request:

```
{app="rental-api"} | json | request_id="d7b0b113-33ec-415e-9c3e-b0e218226021"
```

(Loki/LogQL — adjust for Kibana/Elasticsearch.)

## 2. Metrics

`actix-web-prom` exposes Prometheus-format text at `GET /metrics`. Standard
`http_requests_total`, `http_requests_duration_seconds_bucket` etc. labelled by
`endpoint`, `method`, `status`. Scrape from Prometheus / Grafana Agent on a
reasonable interval (15s is fine).

The endpoint is intentionally unauthenticated and lives at the root, not under
`/api/v1/`. If exposing publicly, gate it at the ingress.

---

## 3. Distributed Traces (OpenTelemetry → Jaeger / Tempo)

### What you get

`tracing-actix-web` opens a root span per HTTP request — `GET /api/v1/bookings`,
`POST /api/v1/bookings`, etc. — annotated with HTTP metadata. Service and
repository functions add `#[tracing::instrument]` so each call becomes a child
span. Example trace tree for `GET /api/v1/bookings`:

```
GET /api/v1/bookings        (tracing-actix-web root span)
└── list                    (services::booking::list)
    └── find_all            (repositories::booking::find_all — wraps the SQL query)
```

For `POST /api/v1/bookings` you additionally see the transactional repository
work and the calendar flip.

Currently the booking domain (services + repositories) is fully instrumented; to
extend coverage to other domains, add `#[tracing::instrument(skip(pool), fields(layer = "service"))]`
(or `layer = "repository"`) to the relevant `pub async fn` items.

### Configuration

| Env var | Effect |
|---|---|
| `OTEL_EXPORTER_OTLP_ENDPOINT` (unset) | OTLP exporter is not started — only logs and metrics are emitted. This is the safe default. |
| `OTEL_EXPORTER_OTLP_ENDPOINT=http://host:4317` | Spans are batched and shipped via OTLP/gRPC to that endpoint. |
| `APP_NAME` | Used as the OTel `service.name` resource attribute. |

Span batching is handled by the SDK (`SdkTracerProvider::with_batch_exporter`).
On graceful shutdown the app calls `provider.shutdown()` so in-flight spans are
flushed; if the process is hard-killed, the last batch is lost.

### Local stack (Jaeger all-in-one)

A `Justfile` target brings up Jaeger:

```
just obs-up      # docker run jaegertracing/all-in-one (UI :16686, OTLP/gRPC :4317, OTLP/HTTP :4318)
just obs-down    # stop + remove
just obs-logs    # tail container logs
```

Then point the app at it and run as usual:

```
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317 cargo run
```

Or uncomment the `OTEL_EXPORTER_OTLP_ENDPOINT` line in `.env`.

Open `http://localhost:16686`, pick **Service: rental-api**, click **Find Traces**.
Each row is one HTTP request; clicking it shows the nested span timeline (root
HTTP span → service span → repository span → individual SQL queries if you
instrument those too).

### Production stack

Two common patterns:

1. **Direct to Jaeger / Tempo** — point `OTEL_EXPORTER_OTLP_ENDPOINT` at the
   collector ingress (e.g. `http://jaeger-collector.observability:4317` inside
   k8s). Simple but couples the app to one backend.

2. **Via OpenTelemetry Collector (recommended)** — run the OTel Collector as a
   sidecar or DaemonSet, point the app at `http://otel-collector:4317`, and let
   the collector route to Jaeger / Tempo / multiple sinks. Lets you swap the
   backend without redeploying the app and adds tail-based sampling.

### Sampling

Currently no sampling is configured — every request emits a full trace. For
high-traffic production this should be moved to head-based or tail-based
sampling at the OTel Collector layer. Search the OTel docs for
`probabilistic_sampler` / `tail_sampling_processor`.

### Correlating a log line with a trace

The `request_id` field on every log line is also the parent span's tag in
Jaeger (visible as `request_id=...` on the root span). Two paths:

- **Logs → Jaeger:** copy the `request_id` UUID from a log line, paste it into
  Jaeger's "Tags" search box: `request_id=<uuid>`.
- **Jaeger → Logs:** in Grafana, configure a Trace-to-Logs link that maps
  `traceID` to a Loki query on `request_id`. Or just copy the request id from
  the trace's root span tags and search Loki / Kibana directly.

## 4. Health checks

`GET /health` returns 200 with `{"status":"ok"}`. Wire it to both Kubernetes
liveness and readiness probes. If you ever add startup-blocking work (DB
warm-up, config fetch), split it into `/health/live` and `/health/ready`.

## 5. Common runbook

**"Where did this 500 come from?"**
1. Get the `x-request-id` header from the failing client response.
2. Search logs for that id → find the `ERROR`-level event with the stack.
3. If OTLP is on, search Jaeger for the same id → see *which DB call / service
   call* failed and how long earlier spans took.

**"Latency suddenly doubled"**
1. Check `/metrics` histograms in Grafana — confirm the rise is real.
2. Open Jaeger, sort traces by duration, pick a slow one — the flame graph tells
   you whether it's a slow SQL query, a contended row lock (visible as time
   between span start and DB acknowledgment), or actix overhead.

**"Trace UI is empty"**
1. `just obs-logs` — verify Jaeger is up.
2. Check the app's startup log — should show `otlp=true` next to `starting application`.
3. Verify `OTEL_EXPORTER_OTLP_ENDPOINT` reaches the collector
   (`docker exec rental-jaeger sh -c 'wget -qO- localhost:14269/'` for in-cluster
   debugging; locally just `curl localhost:16686/api/services`).
4. Spans are batched — give it ~5 seconds after the request before searching.

**"OTel exporter is causing crashes / timeouts"**
- The exporter never blocks the request path; it's a fire-and-forget batch
  processor. If the collector is unreachable, you'll see `WARN`-level lines
  from `opentelemetry_sdk` saying the export failed. The app keeps serving
  traffic.
- To rule it out entirely, unset `OTEL_EXPORTER_OTLP_ENDPOINT` and restart.

## 6. Quick reference

```
# Bring up local observability stack
just db-run         # Postgres
just obs-up         # Jaeger
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317 cargo run

# Generate some traffic
curl http://localhost:8080/api/v1/bookings
curl http://localhost:8080/api/v1/countries

# Inspect
open http://localhost:16686                   # Jaeger UI
curl http://localhost:8080/metrics            # Prometheus metrics
curl -i http://localhost:8080/health          # health + x-request-id
```
